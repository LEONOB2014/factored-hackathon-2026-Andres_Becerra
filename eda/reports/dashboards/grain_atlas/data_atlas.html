The number that shapes every model: 0.81 a month

How much history does a customer have?

If transactions arrive at random at a steady rate λ per month (a Poisson process), the number a customer makes in a window of w months is Poisson with mean λ·w. Change the window and the minimum a feature or a rule needs.

ConceptWhy "a few events" breaks per-customer statistics

Most fraud and credit features compare an event with the customer's own normal: their average amount, their usual hour, their usual merchant. The precision of an average of n values improves with √n: the standard error of a mean is σ/√n. With 5 transactions the customer's "normal amount" is uncertain by about 45 % of the spread (1/√5); with 50 it is about 14 %. A real retail bank sees 20 to 60 card and account movements per active customer per month; this dataset averages 0.81, about 29 over three years.

So deviation-from-self features are mostly noise here, and rules like "three months with inflow in the last six" fail for almost everyone: 144,648 of 150,000 customers (96.4 %) get the credit decline reason R04_INSUFFICIENT_INCOME_HISTORY (module 14).

For modelsWhat to do about it
  • Prefer population-level features (peer group by segment, country, channel, merchant category) over per-customer baselines.
  • Use Bayesian shrinkage when a per-customer statistic is needed: blend the customer's mean with the segment mean, weighted by how many events the customer has (empirical Bayes). With n = 3 the segment dominates.
  • Do not train sequence models (RNN, transformers over event sequences) on this data: there is no sequence to learn.
  • State the limitation in the model card: it is a property of the synthetic generator, not something the pipeline can fix.

ConceptMedallion architecture

A medallion lakehouse arranges data in layers of increasing refinement, usually bronze (raw), silver (cleaned, typed) and gold (business-ready). The value of the pattern is not the names. It is the rule that each layer is derived from the one before by code in version control, so any table can be rebuilt and every value traced back to the bytes it came from. Here the pattern is made strict: bronze is lossless (byte-exact), silver never discards (it flags), and gold is reproducible (same input, same bytes).

ConceptKimball dimensional modelling: facts, dimensions, grain

Ralph Kimball's method organises an analytical warehouse into facts (events you measure: a transaction, a contact) and dimensions (the context you slice by: customer, product, date, channel). A fact table joins to its dimensions through keys, forming a star. Every fact table declares its grain: what exactly one row means ("one transaction", "one customer per month"). Mixing grains is the most common source of double counting.

Surrogate keys are warehouse-generated keys (here md5(id || '|' || version_no)) that identify one version of an entity, so a fact can point to the customer as they were when the transaction happened.

ConceptSCD Type 2: keeping history in a dimension

A Slowly Changing Dimension of Type 2 never overwrites. When an attribute changes (a customer's segment, a credit score), the current row is closed (valid_to set) and a new row opened with a new version number. Questions like "what segment was this customer in when they were offered this loan?" become answerable, which is what credit adverse-action notices, fair-lending reviews and model backtests need.

The source delivers only the current state of customers and products, so the warehouse starts history from the first snapshot it takes. Module 05 shows what would have happened had the backup folder been loaded as a second snapshot.

Why a hash chain makes the audit log tamper-evident

Edit any entry and watch the chain break

Each ledger entry stores the hash of its own content plus the previous entry's hash. Change one character anywhere and every later hash stops matching. This demo uses a small 32-bit hash (FNV-1a) so it runs instantly; the real ledger uses SHA-256.

Why it mattersWhat the audit layer buys a bank

Regulators (CNBV in Mexico, SFC in Colombia, BCRA in Argentina) and internal audit ask the same three questions of any number a bank reports: where did it come from, who changed it, and can you reproduce it. WORM storage answers the first, the hash-chained ledger the second, deterministic rebuilds the third. A hash chain does not prevent an administrator from rewriting the log; it makes any rewrite detectable, and sealing the chain head to WORM storage makes even a full rewrite detectable.

ConceptA foreign key can be valid and still wrong: semantic integrity

A database referential check asks: does the product id in this complaint exist in the products table? For R25 and R26 the answer is always yes, so dbt test relationships passes. The semantic check asks a stricter question: does that product belong to the customer who filed the complaint? For every complaint that names a product, it does not.

In a real bank this is how a dispute ends up investigated on the wrong account, or a regulator complaint report lists products the complainant never held. The control is an ownership-consistency test: join through the product to its owner and compare.

For modelsConsequences, table by table
  • Complaints → transactions: no key exists and product links are wrong, so dispute automation and "which transaction is this complaint about" are blocked. Only 34 of 26,351 disputes link to a transaction with medium or better confidence.
  • Transcripts: template text with one intent value; any NLP model trained on it learns the template. Use it only to prototype the pipeline (ingest, redact, chunk, embed).
  • Surveys: no "Promoter" category exists, so a Net Promoter Score cannot be computed honestly.
  • Campaign sends: no randomised control group, so uplift (the causal effect of a send) is not identifiable.
  • Customers: current state only; tenure is unreliable because 49.9 % of products were opened before their owner registered (R02).

Several patterns are artefacts of the generator: Argentine pesos flat at about 350 per dollar for three years, no MXN anywhere while half the customers are Mexican (their transactions are labelled USD, R17), 99.997 % of customers registered at branches that do not exist (R23). A model that learns these patterns learns the generator. The atlas flags each one so it is never mistaken for signal.

Module 04 · label leakage

The fraud label is a function of a score

is_fraud is true for 4,316 transactions (0.0975 %). It is not an observation of fraud: it is derived from fraud_score. A score of 35 or more always means fraud, and about 45 % of fraud has a low or missing score.

0.824AUC once fraud_score is a feature: the leak

ConceptLabel leakage, in one picture

Leakage happens when a feature carries information about the label that would not be available, or would not be independent, at the moment the model is used. Here the label was computed from a feature. A model given fraud_score rediscovers the rule "score ≥ 35 → fraud" and looks excellent (AUC 0.82, AP 0.57), but it has learned the generator's labelling rule, not fraud. Remove the score and nothing is left: AUC 0.513.

is_fraud = f(fraud_score, noise) ← how the data was made model(fraud_score, amount, hour…) ← learns f, not fraud model(amount, hour, merchant…) ← AUC 0.513: no behaviour to learn
ConceptAUC, average precision and the base rate

ROC AUC is the probability that a randomly chosen fraud is scored above a randomly chosen legitimate transaction. 0.5 is chance, 1.0 is perfect. It ignores how rare fraud is, which makes it flattering when the positive class is tiny.

Average precision (AP) summarises the precision–recall curve: on average over the frauds found, what share of the alerts raised so far were fraud. A random ranking has AP equal to the base rate (the share of positives). So AP must always be read against the base rate: AP 0.0147 against a random 0.0139 means almost nothing was learned.

In the point-in-time test, AP 0.00086 against a base rate of 0.00087: exactly chance.

ConceptPoint-in-time features and out-of-time tests

A point-in-time (PIT) feature uses only data that existed at the moment of the transaction: the customer's last-30-day count as of that second, not as of today. Without it, a model learns from the future and its offline score collapses in production. An out-of-time test trains on earlier months and tests on later ones, which is how a model is actually used. The warehouse's feat_fraud_realtime_pit enforces both; gradient boosting on it (32,954 training rows, 7,559 test rows, weighted) scores AUC 0.504.

Why rare events make alerts mostly false

Bayes' rule: the share of alerts that are real fraud (precision, or positive predictive value) depends on the base rate as much as on the model. Try a very good model at this dataset's fraud rate.

For modelsWhat can and cannot be built
  • No supervised fraud model on is_fraud: it would learn the labelling rule. Any AUC above 0.55 on this label should be treated as a leak until proven otherwise.
  • Unsupervised anomaly detection works without labels and is validated on injected anomalies (module 06).
  • Rules (velocity, new device, amount far above peer group) are explainable and auditable.
  • A real fraud model needs confirmed labels: chargebacks and analyst dispositions, with their delay (a chargeback can arrive 30 to 120 days after the transaction), so training windows must end before labels mature.

Test 1 · can a classifier tell the two folders apart?

ConceptClassifier two-sample test (C2ST)

To ask "do these two samples come from the same distribution?" across dozens of columns at once, label one sample 0 and the other 1, train a classifier, and measure its AUC on held-out rows. If the distributions are identical no classifier can do better than 0.5; the further above 0.5, the more different they are, and the model's feature importances tell you where they differ. It replaces dozens of per-column tests (and their multiple-testing problem) with one.

Reading the chart: customers, products and transactions are statistically indistinguishable (0.498–0.500), which is why the folder looked like a backup. Contact-centre interactions are almost perfectly separable (0.989); digital events (0.536) and sends (0.546) differ a little; complaints come out below 0.5 (0.449), a sign the classifier keys on something that flips between folds rather than a stable difference.

Test 3 · are they the same people under different ids?

Fellegi–Sunter record linkage, by hand

Probabilistic linkage scores a candidate pair of records by how much each field's agreement or disagreement shifts the odds that they are the same person. The m and u values below are illustrative, not the notebook's fitted ones.

fieldm = P(agree | match)u = P(agree | non-match)this pairweight (bits)
ConceptHow Fellegi–Sunter works

For each field, two probabilities: m, the chance that the field agrees when the two records really are the same person (below 1 because of typos and updates), and u, the chance it agrees by coincidence for two different people (high for city, tiny for a document number). Agreement adds log2(m/u) bits of evidence; disagreement adds log2((1−m)/(1−u)), usually negative. The sum is the log of a likelihood ratio, and with a prior it becomes a posterior probability of a match. Pairs above an upper threshold are linked, below a lower one rejected, and the band in between goes to clerical review. In practice m and u are estimated with the EM algorithm on unlabelled pairs, and candidate pairs are restricted by blocking (for example same birth year) so 150,000 × 150,000 comparisons become manageable.

Result here: about 10.5 k people (7 %) appear in both folders, about 7.5 k of them under a different customer id; 93 % of customers have no counterpart.

Test 4 · what if we had loaded it as the next snapshot?

Why it mattersFalse history is worse than no history

Loaded naively, the warehouse would have "learned" that 145,975 records were closed without successor, 1,525 credit scores changed, 1,052 identity-document numbers changed (in a bank, a red flag for identity fraud that triggers review) and 70 consents flipped. None of it happened. An identity-change alert storm, a credit model trained on fictional score migrations, and a consent audit with invented withdrawals would all follow. For modelsHow to use the backup well

As a stability test set: a dataset from the same generator but different individuals. A detector whose performance holds on it generalises beyond the rows it was tuned on. Module 06 uses it exactly that way (COPOD's AP drops 0.133 on it; Isolation Forest's does not).

Ensembles beat every single method

ConceptRank ensembles and Reciprocal Rank Fusion

Detectors output scores on incompatible scales, so they are combined by rank: each method ranks all transactions, and the ensemble averages the ranks (mean rank) or sums 1/(k + rank) (Reciprocal Rank Fusion, RRF, with k usually 60), which rewards being near the top of any list. Combining methods with different blind spots covers more anomaly types. But adding weak methods hurts: averaging all 13 by mean rank gives 0.260, while the top 3 give 0.773. Choose members on a validation split, never on the test split.

Cost of each detector's operating point

Total cost = (false alerts × cost of one review) + (missed anomalies × cost of one miss). The evaluation split holds 1,009 planted anomalies. Each detector's alert budget was optimised for a miss costing 100 reviews; move the ratio to see how the ranking reacts at those budgets.

For modelsDesign consequences
  • Deploy a small rank ensemble (top 3 on validation) as the monitoring detector, plus dedicated rules for dormant reactivation, which no strong detector catches.
  • Choose the alert budget from analyst capacity and the cost ratio, not from AUC.

ConceptFour layers of evidence

The run test: when has a value "died"?

If a category value appears on a share p of days, independently, the gap between appearances is geometric: P(absent n days in a row) = (1 − p)^n. When that probability drops below α, the absence is declared a change.

CUSUM with a permutation test: finding when a series shifted

A daily statistic (say, the median amount) of 120 days, with a shift of δ standard deviations from day 80. The CUSUM of deviations from the overall mean peaks at the change point. The permutation test shuffles the days 499 times: if the real peak is higher than almost every shuffled one, the change is real.

ConceptWhy a permutation test

The maximum of a CUSUM is always positive, even on pure noise, so "the CUSUM peaked" proves nothing. The question is whether it peaked higher than it would on the same values in random order. Shuffling destroys any change point while keeping the distribution of values, so the shuffled peaks form the null distribution. The p-value is (1 + number of shuffled peaks ≥ observed) / (1 + shuffles). No normality assumption is needed, which matters for skewed money amounts.

Why it mattersSilent producer changes are the most expensive data bug

A core-banking upgrade that writes amounts with a decimal comma, restates them in thousands, or translates a category into Spanish does not fail the pipeline. It produces plausible wrong numbers that reach reports and models. These detectors catch each such change on the day it happens; the silver circuit breaker (module 09) then holds the affected partition before it reaches gold.

Lossless bronze: keep the source exactly as written

The first bronze cast values to types while loading, and casting interprets. The lossless zone stores every field as the text it was, with a sha256 per record, and proves it can rebuild the source byte for byte.

ConceptWhy an empty string is not a NULL

In a CSV, ,, (empty) and a missing column are different facts, and both differ from the text "nan" or "NULL". A typed loader maps all of them to NULL, which destroys the evidence needed to tell "the source sent nothing" from "the source sent a broken value". 171.9 M cells lost that distinction. Lossless bronze keeps it, so silver can decide, by contract, what an empty value means for each column.

ConceptThe proof: re-serialise and compare hashes

Each record is parsed, stored as text fields, then re-serialised to canonical CSV and hashed. If the hash equals the hash of the original bytes, the stored fields are provably the source. Every record parsed ok and re-serialised canonically. Build: 8.4 minutes for main with 8 workers; verification 3.7 minutes. On the running stack the 24 proof manifests were sealed to WORM storage with COMPLIANCE retention, and a delete was refused.

For modelsWhat this buys a model

Every feature value can be traced to a file, line and byte range, and the raw text is still there if a contract was wrong. A model-risk reviewer (SR 11-7 style validation) can sample any prediction and walk back to the source record. If a typing rule is found to be wrong next month, silver is rebuilt from bronze; nothing is re-downloaded and nothing is guessed.

CautionA statistic must be stable before it can hold data

The first scale check ran on every numeric column and held 523 transaction partitions on latitude. Not a data defect: the daily median magnitude of coordinates is bimodal (real cities versus "null island" points at 0,0), so it jumps by a factor of 4 on about half the days. The contract generator now measures each column's own history: a column that crosses the scale threshold in more than 5 % of its partitions gets no scale check, with the reason written into the contract (latitude 47 %, longitude 50 %, send cost 45 %). A control that fires on normal days gets switched off by its operators; better not to have it.

ConceptCircuit breaker, in pipeline terms

Borrowed from electrical engineering: when the load is abnormal, break the circuit rather than burn the house. A severity A drift on a partition (column dropped, header gained a column, values in a new format or scale, vocabulary translated) holds that partition: its rows stay in bronze and in the typed models for inspection, but not_held filters them out of staging, gold, features and serving. Airflow opens one review per new hold. Releasing a hold is a four-eyes action (module 10). A severity B change (a rare new category) is reported and flows.

For modelsMonitoring for free

The same per-partition profiles are the inputs of model input-drift monitoring: population stability of each feature's source columns, vocabulary changes, null-share changes. A model monitor can subscribe to the hold and finding tables instead of recomputing them.

Module 10 · phase 4

ConceptWhy reverts and partition releases share the flow

Reverts: the requirement was to "restore or fix". Without a revert, an approved mistake can only be covered by another correction, and silver loses the record of what the source said. With an append-only log, a revert is one more entry that stops an overlay, so it costs almost nothing and completes "restore".

Releases: in phase 3 a held partition was released by adding a row to a seed file in git. That is reviewed, but not bound to an Airflow identity, not in the hash-chained ledger and not four-eyes enforced. Moving it into the same flow gives the circuit breaker and the corrections one audited path.

ConceptRebuild as of any point

An auditor asking "what did the credit mart say on 3 October, before the correction?" gets the exact bytes, not an approximation. This is bitemporal thinking: the time a fact was true in the world versus the time the bank knew it.

Why it mattersFour eyes is a control regulators expect

Segregation of duties (no single person can both make and approve a change to records that feed financial or regulatory reporting) is a standard internal-control requirement in banking. The DAG enforces it in code: the approval task refuses an answer from the proposer and writes the attempt to the ledger.

Why a parallel sum of doubles changes

10,000 random amounts with cents, plus a few very large balances. A database sums them in parallel chunks whose order depends on thread timing. Floating-point addition is not associative, so the order changes the last digits. Exact decimal arithmetic does not care.

Press the button.
ConceptIEEE-754 doubles and associativity

A double has 53 bits of mantissa, about 15–16 significant decimal digits. When a large and a small number are added, the small one is rounded to the large one's precision. So (a + b) + c can differ from a + (b + c): (1e16 + 1) − 1e16 = 0 but (1e16 − 1e16) + 1 = 1. DuckDB aggregates in parallel; the order in which partial sums meet varies from run to run. Casting to DECIMAL(38, 9) makes each addition exact (integers scaled by 10⁹), hence order-free, and the result is cast back to DOUBLE so downstream contracts do not change.

Why it mattersReproducibility is evidence

If two rebuilds of the same data differ, you cannot tell a real change from noise: a model's training set changes under it, a reconciliation never closes, and an auditor cannot verify a reported figure. With 108/108 identity, any difference between builds is a real change and points at its cause. The one-time cost: customer_sk and product_sk took new values, which is breaking for anything that stored them.

ConceptValidating an imputation against the rows that do not need it

2.25 % of transactions lack the source's USD amount, so the pipeline fills it with amount × the published daily rate. ConceptPoint-in-time joins and the validity of the first version

An SCD2 dimension gives each version a validity interval. A fact joins the version that was valid when it happened: t.ts ≥ valid_from and t.ts < valid_to. The platform makes version 1 valid from the customer's registration (or the product's opening). In this data, 19 % of transactions predate registration or opening: registrations are spread over 2018–2026 and transaction dates over 2023–2026, drawn independently. Those transactions fall before version 1 and join nothing.

customer C-42 registered 2025-03-10 version 1: valid 2025-03-10 → ∞ transaction T-9 on 2024-11-02 no version covers 2024-11-02 → customer_sk = NULL

The fix is Kimball's standard convention: the first observed version is valid from the beginning of time (1900-01-01), because before the first snapshot the earliest known state is the best description available. The keys do not change (they hash the version number). Add not_null tests on both keys.

ConceptContribution bounding, sensitivity and the privacy budget

Differential privacy guarantees that a release barely changes whether or not any one person is in the data. Here the bounds cost nothing (no customer exceeds the complaint cap; 0.08 % of customer-months reach the clamp). ε is the budget: smaller is more private and noisier, and budgets add up over repeated releases, so track the cumulative ε in the ledger.

Why it mattersThe law a retention model must beat

Each product is used in about a quarter of months, independently of the customer's other products, so a customer with k products is dormant with probability c·rk. The customer-grain "signal" for dormancy and lapse is this arithmetic of exposure. P(dormant month | k products) = c · rk, r ≈ 1 − P(product used in a month)

ConceptHow a clock is measured from the data alone

If a process was generated with a weekly rhythm on some clock, its hour × weekday table is independent only on that clock: on any other, the weekend boundary cuts through the wrong hours. Shift every timestamp by −12…+12 hours and compute the χ² of independence per degree of freedom: it falls to about 1 at the generator's clock. A second, exact test: on that clock, the shifted timestamp's date equals the batch's process_date for every row.

clock = argmin over s of χ²(hour × weekday | timestamp + s) / dof; check: date(timestamp + s) = process_date

The answer is the delivery day: −6 h for transactions, digital events and sends, −8 h for contacts and complaints, the same in Mexico, Colombia and Argentina. Legal local time (UTC−5 in Colombia, UTC−3 in Argentina) is not the data's clock.

Module 13 · learnability

What a model can and cannot learn here

Learnability is a property of the data, not of the algorithm. A bigger model does not fix a leaking label, a missing key or a missing control group.

modelverdictthe blocking factdata that would unblock it
ConceptThree reasons a model is not learnable
  1. No valid target. The label is missing (credit performance), derived from a feature (fraud) or synthetic text (transcript intents).
  2. No identifiable effect. Causal questions (did this campaign cause a purchase?) need variation that is not chosen by the same process that predicts the outcome: a randomised holdout. Without it any estimate is confounded.
  3. No linkage. The question needs a join the data does not have (complaint → transaction, transfer → counterparty).

When one of these holds, the right deliverable is the pipeline, the contract and the data-collection change that will make the model possible, plus a rule-based version that is honest about what it does.

For modelsThe model-risk checklist that applies to all of them
  • Label audit before training: how was the label produced, when is it known, can a feature encode it?
  • Point-in-time features and out-of-time validation only.
  • AP or cost at the base rate, never AUC alone.
  • Stability on a second population (the backup) and on later months.
  • Reproducible training data (module 11) and lineage to bronze (module 08).
  • A model card with limitations, and a human approval step before serving.
