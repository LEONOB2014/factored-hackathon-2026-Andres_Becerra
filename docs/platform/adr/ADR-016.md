# ADR-016 · Segment by country at bronze, before silver

Status: accepted (2026-10)

## Context
The country series (`eda/notebooks/country_*`) rebuilt the whole platform on each country's data alone with
`latam_eda.country.build_country_lake`. Cutting the lossless bronze, rather than filtering a mart, was what exposed
the national facts:
- a blended contract that holds every day of every country;
- national rule rates (R17 is a Mexican rule; R18 exists only where pesos do);
- 6,926 Argentine complaints pointing at products outside Argentina, which a mart filter would have hidden.

Silver is where contracts, drift checks, imputation and schema evolution are decided. Each of them needs the
country's own population to be correct (ADR-011). On this synthetic dataset the countries behave alike, so the cut
changes no behavioural finding today. Real feeds will differ by market.

## Decision
1. **Every scope is a lossless subset of bronze, cut before silver.** Scopes are `ALL` (the whole bank) and one per
   market: `MX`, `CO`, `AR`.
2. **The cut rules are a platform contract** (`latam_platform.scopes`, ported from the EDA):
   - `customers`: by the customer's country;
   - customer-owned tables (products, transactions, contacts, transcripts, surveys, complaints, sends): by
     `customer_id`, so every join stays complete inside the scope;
   - `digital_events`: by customer, and anonymous events by IP country;
   - shared reference tables (branches, agents, campaigns, exchange rates): linked, not cut;
   - the holdout zone and the quarantined backup: cut by the same rules;
   - corrections and proof manifests: shared.
3. **Each scope has its own lakehouse file and its own gates.** The same compiled dbt project runs on it with the
   scope's seeds (ADR-011), so one country's delivery never blocks another's (ADR-020).
4. **The cut writes a manifest** (`_country_lake.json`): rows total and kept per zone and table, and the rule applied.
   Reconciliation checks that the scopes partition the customer-owned rows.

## Consequences
- Contract baselines, drift references and imputations are estimated per country, on each country's reference window.
- Storage grows by about one copy of the customer-owned bronze (shared tables are links). Compute per scope is
  smaller than for the whole bank, and the scopes can run in parallel.
- Cross-border references stay visible as findings in each scope instead of disappearing in a filter.
- Pooled models still train on `ALL` with a country feature; scopes serve per-country calibration and monitoring.

## Alternatives considered
- **Filter by country in gold or the marts** (rejected): silver decisions would still use the blended population,
  and cross-border references would be filtered out silently.
- **Partition one lakehouse by country** (rejected for now): DuckDB is single-writer, so scopes could not build in
  parallel, and a held partition in one country would block the shared run.
- **One code base per country** (rejected, ADR-011): the methods would drift apart.
