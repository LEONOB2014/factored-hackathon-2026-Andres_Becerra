# ADR-020 · Lateral pipeline expansion: scope × grain

Status: accepted (2026-10)

## Context
`dbt_lakehouse` builds one scope (the whole bank) from seeds to audit. The notebooks already proved two expansions:
- the same compiled SQL per country on a bronze cut (ADR-016);
- aggregate grains on top of gold (ADR-017).

Both ran only in notebooks, by hand. Expanding laterally means the same pipeline, the same tests and the same gates
for every scope and grain, without copying DAG code.

## Decision
1. **One DAG per scope from one factory** (`platform/airflow/dags/lakehouse_scoped.py`). `ALL` stays
   `dbt_lakehouse`; `lakehouse_mx`, `lakehouse_co` and `lakehouse_ar` are generated from the same layer list
   (`latam_dags.common`). Each scope DAG runs:
   1. `cut_bronze`: the country cut (ADR-016), idempotent, with its manifest;
   2. the layer groups `seeds → silver → snapshots → gold → aggregates (day, cell, hour) → features, graph and
      knowledge → privacy and serving → audit`, as Cosmos task groups with tests after each group;
   3. the drift, quality and governance gates of `dbt_lakehouse`, on the scope's lakehouse.
2. **Each scope has its own lake directory and DuckDB file,** passed to dbt through `LATAM_LAKE_DIR` and
   `LATAM_DUCKDB_PATH`. Scopes never contend for the single writer, so they can run in parallel; inside the
   memory-capped scheduler the shared DuckDB pool serialises them until it is given more slots.
3. **Scheduling is asset-driven.** Every scope DAG listens to `BRONZE` and `CORRECTIONS`, and emits its own lakehouse
   asset for downstream consumers (serving, the readiness scorecard, the console).
4. **The grain families are task groups selected by tag** (`grain_day`, `grain_cell`, `grain_hour`), so a scope can
   skip the hour family when its schedule does not need it.
5. **The readiness scorecard runs per scope** once its gate functions are in `latam_platform` (ADR-018).

## Consequences
- A change lands once and runs for every scope. The DAG integrity tests cover all generated DAGs.
- Local runs of all scopes are heavy (four full builds). Development uses `dbt compile`, DAG import checks and builds
  of selected groups. Full runs belong to the remote compute environment (`docs/development/modal.md`).
- Downstream consumers choose a scope by asset rather than by filtering.

## Alternatives considered
- **Copy `dbt_lakehouse` per country** (rejected): the DAGs would drift.
- **One DAG with dynamic task mapping over scopes** (rejected): Cosmos task groups do not map cleanly. One failing
  scope would also mark the whole run failed and block the others' downstream assets.
- **Country as a dbt variable over one lakehouse** (rejected, ADR-016): single-writer contention, and a hold in one
  country would block all.
