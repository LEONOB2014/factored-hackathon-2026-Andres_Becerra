# ADR-006 · DuckDB for development, BigQuery as the analytics layer

Status: accepted (2026-10) · revised 2026-10-05 · related [ADR-007](ADR-007.md), [ADR-009](ADR-009.md),
[ADR-020](ADR-020.md)

## Context
The whole lakehouse must build on a laptop:
- 4.4 M transactions;
- 15.6 M digital events;
- a dozen dbt layers;
- per-country scopes (ADR-020).

In the cloud, analysts need a governed, scalable analytics layer. That layer must respect residency (ADR-007) and
never receive raw personal data.

## Decision drivers
- **Fast, free, reproducible iteration** in development and CI.
- **The same dbt project** compiles for development and for the cloud analytics layer.
- **Raw personal data stays in the lakehouse;** analytics sees tokenised or aggregated data only.
- **Region-pinned analytics** per residency environment.

## Decision
1. **dbt-duckdb** builds the full lakehouse (silver → gold → aggregates → serving and the rest) locally, in CI and in
   Airflow. The profiles bound memory and threads through `LATAM_DUCKDB_MEMORY` and `LATAM_DUCKDB_THREADS`, so builds
   fit the memory-capped scheduler.
2. **BigQuery is the cloud analytics layer, not the transformation engine.** The dbt targets `bq_mx`
   (northamerica-south1) and `bq_br` (southamerica-east1) build BigQuery-native models over tables published per
   region:
   - authorised views;
   - differentially private views;
   - KPI tables.

   This is **designed and validated, not applied**.
3. **Heavy transforms stay in the lakehouse.** BigQuery receives only tokenised gold, serving and privacy outputs.

## Implementation
- `platform/dbt/profiles.yml`: the DuckDB targets with bounded memory and threads; `bq_mx` and `bq_br` marked "not
  applied".
- `platform/dbt/models/bigquery/`: `bq_customer_360_by_country`, `bq_dp_complaints_country_month`,
  `bq_fraud_kpis_daily`, and their sources.
- Terraform: `platform/infra/terraform/gcp/modules/bigquery`.

## Evidence and verification
- The full lakehouse builds green locally and in Airflow (the end-to-end run of 2026-10-03,
  [platform README](../README.md)).
- Two builds of the same commit give identical relations ([reproducibility evidence](../evidence/reproducibility/README.md)).
  Determinism guards ban order-dependent functions (for example `any_value`, rewritten to `min` in the generated
  aggregates, ADR-017).
- The CI dbt job and the governance gate check contracts and metadata on every change.

## Consequences
- **Positive:**
  - laptop and CI builds with no cloud cost;
  - deterministic outputs;
  - one dbt project for both engines;
  - raw data never leaves the lakehouse.
- **Negative:**
  - DuckDB is a single writer: Airflow serialises heavy tasks through a pool (ADR-020);
  - large models need bounded memory and spill;
  - some DuckDB SQL needs dispatch macros if transforms ever move to BigQuery.
- **Risks:**
  - the BigQuery models drift from the DuckDB ones because they are not applied. Mitigated by compiling the `bq_*`
    targets in CI before any apply.

## Alternatives considered
- **Run all dbt in BigQuery** (rejected for now): cost per iteration, and residency complexity for raw personal data
  in the transformation layer. It would win with a cloud-only team and no local constraint.
- **Spark for transformations** (rejected): a cluster to run and pay for, at volumes DuckDB handles on one machine.
- **Postgres as the warehouse** (rejected): row store, slow scans at this volume, and contention with serving
  (ADR-003).

## Revisit when
- **Single-node DuckDB cannot build within the run window:** move the lakehouse to Iceberg with a distributed engine;
  the dbt models stay.
- **The cloud is applied:** run `bq_mx` and `bq_br`, and gate analytics publication per region (ADR-007).

## Revision note
The original text did not state that the BigQuery targets are not applied. Its "laptop builds in about two minutes"
was not backed by a committed measurement and is removed. It also did not name the memory bounds and determinism
guards the builds rely on.
