# ADR-011 · Country-keyed configuration, one code base

Status: accepted (2026-10)

## Context
The platform's contract baselines, rule SLOs, AML thresholds, regulatory deadlines and calendars were set for the
bank as a whole. Rebuilt per country (`eda/notebooks/country_*`), the bank-wide contract would hold every transaction
day of Mexico, Colombia and Argentina (1,099, 1,099 and 1,098 days): typical amounts are 0.09×, 307× and 27× the
blended baseline because the currencies differ. Rule rates are national (R17 is 100 % in Mexico and 0 % elsewhere).
AML reporting lines (USD 7,500 cash in Mexico, COP 10 M in Colombia, an inflation-indexed UIF threshold in Argentina;
general rules that compliance must confirm),
complaint deadlines and consent law differ by country. Behaviour does not: the same compiled SQL runs unchanged on
each country. Evidence: [strategy 12 §12.1](../../strategy/12_development_path.md) E7–E9.

## Decision
One dbt project, with configuration keyed by `(table, country)` in seeds:
- contract baselines (empty share, scale and spread), estimated on each country's reference window;
- rule SLOs: zero-tolerance policies shared, rate-based SLOs re-based per country;
- AML lines in local units, regulatory deadlines per case type, and the country calendar (bank holidays, paydays).

Compliance owns the regulatory seeds. The drift and quality gates are evaluated per country, so one country's data
never blocks another country's run.

## Consequences
- Fixes and features land once for every country, and the country series proves the code needs no fork.
- Seeds become a governed artefact: they are reviewed on change and versioned with the code.
- Gates and dashboards gain a country dimension.

## Alternatives considered
- Bank-wide contracts and SLOs (rejected: they hold every day of every country, or must be disabled for amounts).
- One pipeline per country (rejected: triple maintenance, and the methods drift apart).
