# ADR-005 · Flink for streaming features

Status: accepted (2026-10) · revised 2026-10-05 · related [ADR-012](ADR-012.md), [ADR-018](ADR-018.md)

## Context
Real-time fraud scoring needs features over event-time windows (counts and amounts over the last hours and days)
when a transaction arrives. A model trained on batch features and served on differently computed streaming features
fails quietly: the classic training/serving skew. Late and out-of-order events are normal in card networks.

## Decision drivers
- **Identical feature semantics in batch and stream,** provable per transaction.
- **Event time with watermarks** and exactly-once state.
- **A managed option in the target cloud.**
- **Bounded latency** for a decision in the authorisation path.

## Decision
1. **Transport:** Redpanda (Kafka API) locally, Managed Kafka in GCP (Terraform module `managed_kafka`, not applied).
2. **Features in Flink SQL** (`platform/flink/sql/fraud_features.sql`). Each window view has one `OVER` frame, joined
   per transaction; checkpoints go to a shared filesystem.
3. **The scorer** (`platform/services/fraud_scorer`, behind Kong) completes history features from batch-warmed state,
   scores, and appends to `decisions.fraud_decision_log` with the model version and reason codes.
4. **Parity is a gate, not a hope.** `stream_demo` compares every streamed transaction's features with dbt's
   `features.feat_fraud_stream_parity`, computed by the same macro over history plus holdout. Any mismatch fails the
   run.

## Implementation
- `platform/flink/` (image and SQL);
- `platform/services/fraud_scorer/scorer.py`;
- `platform/airflow/dags/stream_demo.py`;
- `platform/libs/latam_platform/stream.py` (replay and parity).

## Evidence and verification
On the 2026-10-03 run ([platform README](../README.md)):
- 38,149 events replayed in 135 s;
- **Flink vs dbt parity: 0 mismatches on all 5 features for 7,789 transactions.**

**Defects found by the parity gate and fixed:**
- **Window merge:** the planner merged windows with the same PARTITION BY and ORDER BY and compiled a 7-day window
  as 24 h, giving 1,865 mismatches on `tx_count_7d`. Fixed with distinct equivalent partition keys per window;
  EXPLAIN shows 3 frames.
- **Idle watermark:** the last windows were never emitted because an idle source after a finite replay holds the
  watermark. Fixed with one warm-up sentinel per partition.
- **Checkpoint storage:** the job kept restarting because JobManager checkpoint storage caps state at 5 MB. Fixed
  with filesystem checkpoints on a shared volume.

## Consequences
- **Positive:**
  - exactly-once, event-time features;
  - a per-transaction proof that serving equals training;
  - decisions logged with versions and reasons.
- **Negative:**
  - more moving parts than a Python consumer (JobManager, TaskManager, checkpoints);
  - SQL planner behaviour must be checked with EXPLAIN, as the window-merge defect showed.
- **Risks:**
  - planner upgrades silently changing window semantics. Mitigated: parity runs on every demo and the run fails on
    any mismatch.

## Alternatives considered
- **A Python stream processor** (rejected for production): lighter, but no exactly-once windowing at scale, and the
  parity proof would rest on hand-written state code. It remains fine for prototypes.
- **Spark Structured Streaming** (not chosen): micro-batch latency and a heavier footprint for this volume.
- **Batch-only features at decision time** (rejected): stale by up to a day, exactly when fraud bursts happen.

## Revisit when
- **A fraud model passes its readiness gate** (ADR-012, ADR-018). Today the label leaks (`fraud_score ≥ 35` ⇒
  fraud) and behavioural models are at chance, so streaming features have no model worth serving yet.
- **Throughput needs managed Flink** in the cloud.
