# ADR-013 · Data completeness and dataset identity controls

Status: accepted (2026-10)

## Context
`data_backup_20260831` was run through the whole platform as if it were the source
(`eda/notebooks/backup_*`, `dataset_compare/01`):
- Its transactions stop 20 months early and two source tables are missing, and **no control noticed**: drift checks
  and data tests judge only the partitions that exist.
- The circuit breaker correctly held every call-centre and campaign day (content rule breaks), but staging silently
  dropped them, so marts and models downstream were empty without saying why.
- Only the reconciliation control (`audit_backup_reconciliation`) showed it was a different dataset: no shared
  transaction is identical.

Evidence: [strategy 12 §12.1](../../strategy/12_development_path.md) E11.

## Decision
Add controls on what *should* arrive and on what a dataset *is*:
1. **Expected-partition calendar** per fact table: every day from first landing to `data_end` must exist, or the
   run holds (severity A).
2. **Row-count floors** per source table: a table that lands empty fails.
3. **Empty windows and splits fail loudly**: fraud splits, eligibility windows and label windows that contain no
   data stop the build instead of producing an empty or censored set.
4. **Hold status flows downstream**: marts and serving tables carry `source_held` (or a freshness date), so "no data"
   and "no activity" differ.
5. **Reconciliation fingerprint on restore**: the share of identical records among shared keys is computed whenever
   a copy is restored. A backup must give 100 %.

## Consequences
- The backup-as-main run becomes the acceptance test: it must be held, while main passes.
- More holds are possible on real feeds, each with an owner and a release path (the four-eyes correction flow).

## Alternatives considered
- A freshness check on the latest partition only (rejected: it misses gaps and missing tables).
- Relying on the drift checks (rejected: they cannot see what did not arrive).
